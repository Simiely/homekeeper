# 开发指南

面向后续维护与功能扩展。遵循「分层 + 模块化」，新增功能不需要改动既有结构。

---

## 目录结构

```
homekeeper/
├── README.md                  # 总导航
├── docker-compose.yml / Dockerfile / .env.example / requirements.txt
├── data/                      # SQLite（卷挂载）
├── app/
│   ├── main.py                # 入口：路由挂载 / 静态 / CORS / lifespan
│   ├── config.py              # 读 .env
│   ├── database.py            # 引擎 / Session / Base / init_db / get_db
│   ├── deps.py                # get_current_user（JWT 校验）
│   ├── core/security.py       # 密码哈希 + JWT
│   ├── models/                # ORM（每表一文件 + __init__ 汇总）
│   ├── schemas/               # Pydantic 请求/响应
│   ├── routers/               # 路由（按资源拆分，/api 前缀）
│   └── static/                # 原生前端（html/css/js 模块化）
├── tests/                     # pytest
└── docs/                      # 专项文档
```

---

## 分层约定

| 层 | 职责 | 不做什么 |
|----|------|---------|
| `models` | SQLAlchemy ORM 定义 | 不写业务逻辑 |
| `schemas` | 请求/响应校验与序列化 | 不碰数据库 |
| `routers` | 接收请求、调用、返回 | 复杂逻辑下沉到 `services/`（预留） |
| `core/security` | 密码 + JWT | — |
| `static` | 原生前端，通过 `api.js` 调后端 | 不直连数据库 |

---

## 如何新增一个资源（示例：品牌 Brand）

1. **模型**：`app/models/brand.py` 定义 `Brand(Base)`，并在 `app/models/__init__.py` 导入。
2. **Schema**：`app/schemas/brand.py` 定义 `BrandCreate / BrandUpdate / BrandOut`。
3. **路由**：`app/routers/brands.py` 写 CRUD，所有写操作加 `current_user: User = Depends(get_current_user)` 做数据隔离。
4. **注册**：`app/main.py` `app.include_router(brands.router)`。
5. **前端**：加 `app/static/js/brands.js` 与 `index.html` 导航项（参考 `items.js`）。

> 保持每资源「model + schema + router」三件套，结构一致即可维护。

## API 约定

- 统一前缀 `/api`，标签按资源（`tags=["items"]` 等）。
- 鉴权：`Authorization: Bearer <token>`；未带/失效返回 401。
- 响应使用 `response_model`，过滤字段统一。
- 错误：`raise HTTPException(status_code=..., detail="中文说明")`。

## 代码规范

- 后端 Python：全程类型注解；枚举用 `str, enum.Enum`（中文值需前后端一致）。
- 前端：原生 ES Module，`api.js` 统一封装 `fetch` 与令牌；视图逻辑拆分到各 `js` 模块；共用函数放到 `static/js/utils.js`。
- 配置一律走 `.env` / 环境变量，不硬编码密钥。
- 多行配置（如 PEM 密钥）用 base64 编码为单行存 `.env`，或在数据卷中存独立文件。
- 新增坑及时补 [踩坑与排错](docs/03-踩坑与排错.md)；发版更新 [更新日志](docs/02-更新日志(CHANGELOG).md)。

## 关键架构决策

### 外键策略
| 关系 | ondelete | 理由 |
|------|----------|------|
| `Item.location_id` → `Location` | `SET NULL` | 删位置时物品保留 |
| `Item.category_id` → `Category` | `SET NULL` | 删分类时物品保留 |
| `ItemImage.item_id` → `Item` | `CASCADE` | 删物品时图片记录自动清理 |
| `PushSubscription.user_id` → `User` | `CASCADE` | 删用户时订阅自动清理 |
| `ItemTag` 关联表 | `CASCADE` | 删物品/标签时关联自动清理 |

### 多对多关系模式
```python
# 1. 独立关联表文件 app/models/item_tag.py
from sqlalchemy import Column, ForeignKey, Integer, Table
item_tag_assoc = Table("item_tags", Base.metadata, ...)

# 2. 模型中使用 secondary + back_populates
class Item(Base):
    tags: Mapped[list["Tag"]] = relationship(
        secondary=item_tag_assoc, back_populates="items", lazy="selectin"
    )
```
`lazy="selectin"` 在查列表时自动 JOIN 加载标签，避免 N+1 问题。

### 图片存储架构
```
data/images/{item_id}/{uuid}.webp
  ├── Django 卷持久化，重建不丢
  ├── 上传时自动 WebP 压缩 + 2000px 缩放
  └── 服务 URL: GET /api/images/{item_id}/{filename}（O(1) 直接读取）
```

### 推送通知架构
```
APScheduler（每 6 小时）
  └── 遍历所有用户
        └── 查 3 天内过期物品？
              └── 推送给该用户的所有 PushSubscription
                    └── 410 Gone → 自动清理
VAPID 密钥首次启动自动生成，存于 data/vapid.json
```

## `services/` 目录（预留）

当路由中的业务逻辑变得复杂时（例如超过 50 行），将其提取到 `app/services/` 下。例如：

- `app/services/expiry_service.py` — 过期扫描与推送逻辑
- `app/services/image_service.py` — 图片处理与清理

目前逻辑简单，直接放在 `routers/` 中，后续按需迁移。
