# 开发指南

面向后续维护与功能扩展。遵循「分层 + 模块化」，新增功能不需要改动既有结构。

---

## 目录结构

```
homekeeper/
├── README.md                  # 总导航
├── docker-compose.yml / Dockerfile / .env.example / requirements.txt
├── data/                      # SQLite + backups + images（卷挂载）
├── app/
│   ├── main.py                # 入口：路由挂载 / 静态 / CORS / lifespan（含 seed admin）
│   ├── config.py              # 读 .env
│   ├── database.py            # 引擎 / Session / Base / init_db / get_db
│   ├── deps.py                # get_current_user / get_admin_user（JWT 校验）
│   ├── core/security.py       # 密码哈希 + JWT
│   ├── models/                # 11 个 ORM 模型 + item_tag 关联表（每表一文件）
│   ├── schemas/               # Pydantic 请求/响应
│   ├── routers/               # 13 个路由模块（按资源拆分，薄壳）
│   ├── services/              # 业务逻辑（9 个：audit/backup/scheduler/push_scheduler + 5 个业务 service）
│   └── static/                # 原生前端（html/css/js 模块化）
├── tests/                     # pytest
└── docs/                      # 专项文档
```

## 分层约定

| 层 | 职责 | 不做什么 |
|----|------|---------|
| `models` | SQLAlchemy ORM 定义 | 不写业务逻辑 |
| `schemas` | 请求/响应校验与序列化 | 不碰数据库 |
| `routers` | 接收请求、调用 service、返回 | 不写业务逻辑（保持薄壳） |
| `services` | 复杂业务逻辑（CRUD/聚合/文件处理/调度） | 不依赖 FastAPI（抛领域异常，router 转 HTTP） |
| `core/security` | 密码 + JWT | — |
| `static` | 原生前端，通过 `api.js` 调后端 | 不直连数据库 |

## 如何新增一个资源（示例：品牌 Brand）

1. **模型**：`app/models/brand.py` 定义 `Brand(Base)`，并在 `app/models/__init__.py` 导入。
2. **Schema**：`app/schemas/brand.py` 定义 `BrandCreate / BrandUpdate / BrandOut`。
3. **路由**：`app/routers/brands.py` 写 CRUD，所有写操作加 `current_user: User = Depends(get_current_user)` 做数据隔离。
4. **注册**：`app/main.py` `app.include_router(brands.router)`。
5. **前端**：加 `app/static/js/brands.js` 与 `index.html` 导航项（参考 `items.js`）。

> 保持每资源「model + schema + router」三件套，结构一致即可维护。

## API 约定

- 统一前缀 `/api`，标签按资源（`tags=["items"]` 等）。
- 鉴权：`Authorization: Bearer <token>`；未带/失效返回 401。
- 管理员鉴权：使用 `get_admin_user` 依赖，非管理员返回 403。
- 响应使用 `response_model`，过滤字段统一。
- 错误：`raise HTTPException(status_code=..., detail="中文说明")`。

## 无头浏览器自动化调试（Edge + CDP）⭐ 重点

> **为什么需要**：纯后端 pytest 测不了前端交互（点击/拖拽/弹窗/样式），而手动操作 + 截图反馈效率低。
> 用无头浏览器真实打开页面、模拟鼠标键盘、抓取 Console 异常与网络错误、自动截图，
> 一轮就能定位前端 bug，**无需人工参与**。这是本仓库前端调试的首选手段。

### 1. 技术选型

| 组件 | 说明 |
|---|---|
| **puppeteer-core** | 只驱动浏览器，不内置 Chromium（体积小）。装在 Node 隔离工作区，不污染全局 |
| **系统 Edge** | Windows 自带 `msedge.exe`，直接用 `executablePath` 指向它，**免下载浏览器** |

```bash
# 安装（仅一次）
cd C:/Users/260531/.workbuddy/binaries/node/workspace
C:/Users/260531/.workbuddy/binaries/node/versions/22.22.2/npm.cmd install puppeteer-core --no-audit --no-fund
```

### 2. 启动方式（环境变量）

```bash
cd <仓库>/homekeeper/browser_debug   # 入库脚本在仓库内，工作区根目录的 browser_debug 仅为本地临时调试
NODE_PATH="<Node workspace>/node_modules" \
  "<Node 安装路径>/node.exe" <脚本名>.js
```

> ⚠️ **重点**：必须用 `NODE_PATH` 指向 workspace 的 `node_modules`，否则 `require("puppeteer-core")` 找不到包。

### 3. 现有脚本清单

| 脚本 | 用途 | 关键验证点 |
|---|---|---|
| `basic_check.js` | 连通性验证 | 自动登录、进位置页、展开物品列表、抓 console/4xx |
| `drag_test.js` | 拖拽结构对比 | 拖拽前后父子关系 diff、zone 状态、移动位置输出 |
| `edit_mode_test.js` | 编辑模式验证 | 编辑开关切换、改名保存、编辑模式下不弹改名、真实拖拽 |
| `drag_gap_test.js` | 拖拽放置验证 | **先按住触发拖拽（间距拉开）再动态扫描缝隙**，验证 after/child 放置生效 |

### 4. 核心 API 速查（重点）

```js
const puppeteer = require("puppeteer-core");
const EDGE = "C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe";

const browser = await puppeteer.launch({
  executablePath: EDGE,
  headless: "new",                       // 无界面运行；可改 "false" 看真实窗口
  args: ["--no-sandbox", "--disable-gpu", "--window-size=1280,900"],
});
const page = await browser.newPage();
await page.setViewport({ width: 1280, height: 900 });

// ---- 抓取异常（每轮必挂，问题定位的命脉）----
page.on("console", (m) => {
  if (["error", "warning"].includes(m.type())) console.log(`[${m.type()}] ${m.text()}`);
});
page.on("pageerror", (e) => console.log("[pageerror]", e.message));
page.on("response", (r) => { if (r.status() >= 400) console.log(`[${r.status()}] ${r.url()}`); });

// ---- 登录（处理导航跳转：page.type + Promise.all 等待）----
await page.type("#username", "admin");
await page.type("#password", "密码");
await Promise.all([
  page.waitForNavigation({ waitUntil: "networkidle2" }).catch(() => {}),
  page.click("#submit-btn"),
]);

// ---- 真实鼠标拖拽（轨迹插值，模拟人手）----
await page.mouse.move(x1, y1);
await page.mouse.down();
for (let i = 1; i <= 20; i++) {              // 20 步插值
  const t = i / 20;
  await page.mouse.move(x1 + (x2 - x1) * t, y1 + (y2 - y1) * t);
  await new Promise((r) => setTimeout(r, 20));
}
await page.mouse.up();

// ---- 读取页面真实状态（比截图更精确）----
const state = await page.evaluate(() => ({
  btn: document.querySelector("#loc-edit-toggle")?.textContent,
  zone: (() => {
    const z = document.querySelector(".loc-gap-zone");
    return z ? { display: getComputedStyle(z).display, opts: [...z.querySelectorAll(".gap-opt")].map(o => o.textContent) } : null;
  })(),
}));

await page.screenshot({ path: "shots/xx.png" });  // 截图留证
await browser.close();
```

### 5. 已踩过的坑（重点 ⚠️）

| 坑 | 说明 | 解法 |
|---|---|---|
| **`node install` 报 MODULE_NOT_FOUND** | 直接调 `node.exe` 不是 npm | 用 `npm.cmd install` |
| **登录后执行上下文销毁** | `evaluate` 里 `form.requestSubmit()` 触发导航，上下文被销毁报错 | 改用 `page.type` + `page.click`，配合 `Promise.all` 等待导航 |
| **`execution context destroyed`** | 同上，导航期间操作旧页面 | 所有导航动作用 puppeteer 原生 API，不在 evaluate 里触发跳转 |
| **拖拽测不准（缝隙找不到）** | 没进入拖拽态时间距未拉开，head 之间缝隙 < 20px | **先 `mouse.down` + 小移动触发拖拽，等间距拉开（sleep 300ms）再扫描缝隙** |
| **401 是"假错误"** | 登录前资源请求 401 属正常（重定向 login.html） | 过滤 `login.html` / `favicon.ico` / `net::ERR_ABORTED` |
| **evaluate 里 `document.querySelector` 找不到元素** | 页面未渲染完/视图未切换 | 先 `waitForSelector` 再 evaluate |

### 6. 推荐工作流（重点）

```
1. 改前端代码 → 语法检查（node --check）→ 服务 200
2. 写/复用浏览器脚本：真实打开 → 登录 → 进入目标视图
3. 模拟操作（点击/拖拽）→ 抓 console / pageerror / 4xx
4. 读取 DOM 状态 + 截图 → 对比预期
5. 修复 → 重跑脚本确认 → 恢复测试数据（用 reorder / API 还原）
```

> 💡 **提示**：拖拽类测试会真实改动数据，跑完记得恢复（见 `drag_test.js` 里结构 diff + reorder 还原的做法）。

## 代码规范

- 后端 Python：全程类型注解；枚举用 `str, enum.Enum`（中文值需前后端一致）。
- 前端：原生 ES Module，`api.js` 统一封装 `fetch` 与令牌；视图逻辑拆分到各 `js` 模块；共用函数放到 `static/js/utils.js`。
- 配置一律走 `.env` / 环境变量，不硬编码密钥。
- 多行配置（如 PEM 密钥）用 base64 编码为单行存 `.env`，或在数据卷中存独立文件。
- 新增坑及时补 [踩坑与排错](docs/03-踩坑与排错.md)；发版更新 [更新日志](docs/02-更新日志(CHANGELOG).md)。

## 关键架构决策

### 外键策略
| 关系 | ondelete | 理由 |
|------|----------|------|
| `Item.location_id` → `Location` | `SET NULL` | 删位置时物品保留 |
| `Item.category_id` → `Category` | `SET NULL` | 删分类时物品保留 |
| `ItemImage.item_id` → `Item` | `CASCADE` | 删物品时图片记录自动清理 |
| `PushSubscription.user_id` → `User` | `CASCADE` | 删用户时订阅自动清理 |
| `ItemTag` 关联表 | `CASCADE` | 删物品/标签时关联自动清理 |

### 多对多关系模式
```python
# 1. 独立关联表文件 app/models/item_tag.py
from sqlalchemy import Column, ForeignKey, Integer, Table
item_tag_assoc = Table("item_tags", Base.metadata, ...)

# 2. 模型中使用 secondary + back_populates
class Item(Base):
    tags: Mapped[list["Tag"]] = relationship(
        secondary=item_tag_assoc, back_populates="items", lazy="selectin"
    )
```
`lazy="selectin"` 在查列表时自动 JOIN 加载标签，避免 N+1 问题。

### 图片存储架构
```
data/images/{item_id}/{uuid}.webp
  ├── Docker 卷持久化，重建不丢
  ├── 上传时自动 WebP 压缩 + 2000px 缩放
  └── 服务 URL: GET /api/images/{item_id}/{filename}（O(1) 直接读取）
```

### 推送通知架构
```
APScheduler（每 6 小时）
  └── 遍历所有用户
        └── 查 3 天内过期物品？
              └── 推送给该用户的所有 PushSubscription
                    └── 410 Gone → 自动清理
VAPID 密钥首次启动自动生成，存于 data/vapid.json
```

## `services/` 目录

业务逻辑统一下沉到 `app/services/`（router 保持薄壳，只做参数校验 + 调用 + 响应映射）：

| 模块 | 功能 |
|------|------|
| `item_service.py` | 物品 CRUD / 筛选 / 分页 / 批量 / 二维码 / 日志 / 磁盘图片清理 |
| `location_service.py` | 位置 CRUD / 层级树 / 拖拽重排（归属、父级、环检测）|
| `dashboard_service.py` | 概览 SQL 聚合统计 / 临期与保修到期提醒 |
| `image_service.py` | 图片 WebP 转码 / 磁盘路径 / 上传 / 列表 / 删除 |
| `data_service.py` | CSV 导入导出 / ZIP 打包 |
| `backup.py` | 自动备份 + 恢复 + 清理（APScheduler）|
| `audit.py` | SQLAlchemy 事件监听 → 自动记录物品变更日志 |
| `scheduler.py` | 调度器统一编排 |
| `push_scheduler.py` | Web Push 订阅管理 + 过期扫描调度 |

> 服务层**不依赖 FastAPI**：业务异常用领域异常（如 `ItemNotFoundError`）抛出，由 router 捕获转换为 HTTP 响应。

## 测试覆盖建议

## 外部服务集成

当 HomeKeeper 需要推送消息到外部服务（企业微信、邮件、短信等），遵循以下约定：

| 原则 | 说明 |
|------|------|
| 配置化 | 所有外部服务的凭据/URL 走 `.env`，不硬编码 |
| 降级不影响核心 | 外部服务不可用时，HomeKeeper 自身功能不受影响 |
| 统一通道 | 通知调度在 `services/push_scheduler.py`，新增通道即为新增 `_send_to_xxx()` 函数 |
| 文档独立 | 推送通道规划见 [docs/07-推送方案汇总.md](docs/07-推送方案汇总.md) |

### 推送通道架构

```
APScheduler 定时器（services/push_scheduler.py）
  └── _check_all_users()
        └── 遍历用户
              ├── Web Push（浏览器推送，已实现）
              └── 邮件 / 企业微信（备选方案，见 docs/07）
```

新增通道只需在 `_check_all_users()` 中增加调用，无需改动定时器逻辑。
